# 1인 개발 MVP 배포 아키텍처, 나는 왜 ECS 대신 "EC2 한 대"를 골랐나

> 작성일: 2026-10-26
> 관련 문서: [DEPLOY.md](./DEPLOY.md), [PLAN.md](./PLAN.md)

## 들어가며

거울샷 스팟을 찾아 주는 앱 **yar-mirror**를 만들고 있다. 백엔드는 Spring Boot와 PostgreSQL(PostGIS)이고, 클라이언트는 Expo(React Native)다. 기능 개발이 어느 정도 끝나서 배포 방법을 정해야 했다.

이전 프로젝트에서는 **GitHub Actions로 CI/CD를 돌리고, AWS EC2·ECS·S3로 배포**했다. 이번에도 그대로 할지, 무료 클라우드로 비용을 0원에 맞출지 고민했다. 이 글은 그 결정 과정을 정리한 기록이다.

**결론부터 말하면 EC2 1대 + Docker Compose + S3 + GitHub Actions로 정했다. ECS, ALB, RDS는 일부러 뺐다.**

---

## 1. 먼저 제약 조건을 정리했다

인프라를 고르기 전에 "이 서비스가 꼭 필요로 하는 것"부터 적었다.

| 제약 | 내용 | 영향 |
|---|---|---|
| **PostGIS 필수** | 주변 스팟 검색에 `ST_DWithin`, `ST_Distance` 네이티브 쿼리를 쓴다 | 아무 관리형 DB나 쓸 수 없다. PostGIS를 지원하는 관리형 DB는 무료 티어가 없거나 비싸다 |
| **사진 업로드** | 서버가 presigned URL을 발급 → 클라이언트가 직접 PUT → 서버가 존재를 확인하는 2단계 흐름 | 사진은 서버 디스크가 아니라 오브젝트 스토리지에 두는 게 맞다 |
| **JVM 서버** | Spring Boot + JPA + Flyway + Security. 기동에 수 초~수십 초, 메모리는 300~500MB | 콜드 스타트가 있는 서버리스나 슬립형 무료 PaaS와는 맞지 않는다 |
| **HTTPS 도메인** | 카카오 OAuth redirect URI, 카카오 JS 키 도메인 등록, iOS ATS | 실제 도메인과 HTTPS가 처음부터 필요하다 |
| **1인 개발 + MVP** | 운영에 쓸 시간이 적고 트래픽은 아직 작다 | 구성은 단순하게, 비용은 낮게 |

## 2. 검토한 후보

### 후보 A. 예전에 쓰던 풀 AWS (ECS Fargate + ALB + RDS + S3)

가장 익숙하고 "정석"에 가까운 구성이다. 하지만 MVP 기준으로 비용을 계산해 보니 맞지 않았다.

- ALB: 트래픽이 없어도 시간당 요금이 붙어 월 약 $18
- Fargate 태스크(0.5vCPU/1GB) 상시 실행: 월 약 $18
- RDS PostgreSQL(PostGIS 확장) 최소 사양: 월 약 $15~25
- **합계 월 $50~70 (7~10만 원)**

사용자가 거의 없는 단계에서 오토스케일링, 무중단 롤링 배포, 관리형 DB 페일오버는 **아직 쓸 일이 없는 기능**이다. 그 기능 값을 매달 내는 셈이다.

### 후보 B. 비용 0원 조합 (Oracle Cloud Free + Cloudflare R2)

- Oracle Always Free ARM VM: 0원이고 서울·춘천 리전이 있다
- Cloudflare R2: 10GB 무료, egress 무료
- 도메인 값만 들어서 **사실상 월 0원**

가장 싸다. 그래도 고르지 않은 이유는 세 가지다.

- 무료 ARM 인스턴스는 생성할 때 "Out of capacity"로 막히는 경우가 꽤 있다고 한다.
- CPU를 거의 쓰지 않는 인스턴스는 유휴 상태로 보고 회수될 수 있다는 정책이 있다.
- **처음 써 보는 콘솔, 네트워크, 권한 체계를 새로 익혀야 한다.** 1인 개발자에게 이건 돈보다 비싼 시간이다.

### 후보 C. EC2 1대 + Docker Compose + S3 ← 선택

ECS·ALB·RDS를 빼고, **EC2 한 대에 앱과 DB를 컨테이너로 같이 올린다.** 사진만 S3에 둔다.

---

## 3. 비용 비교 (서울 리전, 대략치)

| 구성 | 월 비용 |
|---|---|
| A. ECS + ALB + RDS + S3 | 약 $50~70 |
| **C. EC2 + Compose + S3** | **약 $20** |
| B. Oracle Free + R2 | 약 $0 (+ 도메인) |

C의 내역은 이렇다.

- EC2 t4g.small (2vCPU, 2GB, ARM): 약 $15
- EBS gp3 20GB: 약 $2
- 퍼블릭 IPv4: 약 $3.6 (2024년부터 유료가 됐다)
- S3: 사진 몇 GB 수준이면 1달러 미만

> 가격은 바뀔 수 있다. 신규 계정은 프리티어 크레딧으로 초기 몇 달이 더 싸질 수 있다.

**B보다 월 2만 원 남짓 더 들지만, A보다 3~5배 싸다.**

---

## 4. C를 선택한 근거

### 근거 1. 익숙함도 비용이다

GitHub Actions, IAM, EC2, S3는 이미 써 봤다. 낯선 플랫폼에서 하루를 막히는 비용이 월 2만 원보다 크다고 판단했다. MVP에서 가장 중요한 건 **빨리 출시해서 검증하는 것**이다.

### 근거 2. 지금 필요한 것만 산다

ECS가 주는 오토스케일링, 롤링 배포, 서비스 디스커버리는 트래픽이 생긴 뒤에 필요한 기능이다. 지금은 컨테이너 3개(Caddy, Spring Boot, PostGIS)를 Docker Compose로 띄우는 것으로 충분하다. 로컬 개발 환경도 이미 `docker-compose.yml`로 PostGIS를 띄우고 있어서, **개발 환경과 운영 환경이 거의 같아진다.**

### 근거 3. PostGIS는 같은 VM 컨테이너가 가장 싸다

RDS에서도 PostGIS 확장을 쓸 수 있지만 최소 사양만으로 월 $15 이상이다. `postgis/postgis` 이미지를 EBS 볼륨에 올리면 추가 비용이 없다. 대신 백업은 직접 챙겨야 해서, **매일 `pg_dump`를 S3에 올리는 cron**으로 해결했다.

### 근거 4. 사진은 처음부터 S3

사진 업로드는 이미 presigned URL 방식으로 설계되어 있다. 클라이언트가 S3에 직접 PUT하기 때문에 사진 바이트가 Spring 서버를 거치지 않는다.

- 서버 메모리와 대역폭을 아낄 수 있다.
- EC2가 망가져도 사진은 남는다. 서버는 "DB 볼륨만 가진, 언제든 다시 만들 수 있는 박스"가 된다.
- S3 egress는 월 100GB까지 무료다. 사진을 클라이언트에서 리사이즈해 장당 300KB 정도로 올린다고 가정하면, 대략 30만 회 조회까지 무료다.

### 근거 5. 되돌리기 쉽다

이 결정에서 가장 마음에 든 점이다. 잘못 골랐어도 갈아타기 쉽다.

- **스토리지:** S3와 Cloudflare R2는 같은 S3 SDK를 쓴다. egress 비용이 문제가 되면 endpoint와 키만 바꿔 R2로 옮기면 된다.
- **컴퓨팅:** compose에서 쓰는 앱 이미지를 그대로 ECS 태스크로 옮길 수 있다.
- **DB:** `pg_dump`로 덤프하고 RDS에 복원하면 된다.

**확장이 필요해지는 시점에 그 부분만 관리형으로 바꾸면 된다.** 처음부터 전부 관리형으로 시작할 이유가 없다.

## 5. 최종 아키텍처

```
GitHub Actions
 ├ PR          : ./gradlew test
 └ main push   : arm64 Docker 이미지 빌드 → ECR push
                 → SSM Run Command로 EC2에서 docker compose pull && up -d
                 (AWS 인증은 OIDC, Access Key를 저장하지 않음)

EC2 t4g.small (ap-northeast-2)
 ├ Caddy        : Let's Encrypt 자동 HTTPS, 리버스 프록시
 ├ Spring Boot  : prod 프로필
 └ PostGIS      : EBS 볼륨, 매일 pg_dump → S3 backups/

S3   : spots/* 사진 (presigned PUT)
웹   : Expo web export → 정적 호스팅
모바일: EAS Build → TestFlight / 내부 테스트
```

### 신경 쓴 디테일

- **SSH 대신 SSM으로 배포:** 22번 포트를 아예 닫는다. 보안그룹에는 80/443만 연다.
- **GitHub Actions ↔ AWS는 OIDC로 연결:** 장기 Access Key를 GitHub Secrets에 저장하지 않는다.
- **DB 포트는 외부에 노출하지 않는다:** compose 내부 네트워크에서만 접근한다.
- **Caddy:** Nginx와 certbot을 따로 설정할 필요 없이 몇 줄로 HTTPS 인증서 발급과 갱신이 된다.
- **ARM(t4g):** 같은 사양에서 x86보다 싸다. 대신 이미지를 arm64로 빌드해야 한다.

## 6. 포기한 것

공짜는 없다. 이 구성에서 감수하는 것들이다.

- **단일 장애점:** EC2 한 대가 죽으면 서비스가 멈춘다. MVP 단계에서는 감수하기로 했다.
- **배포할 때 잠깐의 다운타임:** `compose up -d`로 재기동할 때 수 초~수십 초 끊긴다. 롤링 배포는 ECS로 옮길 때 해결한다.
- **DB 운영은 내 몫:** 백업, 복원 연습, 버전 업그레이드를 직접 해야 한다.
- **월 2만 원:** 0원 조합보다는 비싸다.

---

## 7. 언제 다시 바꿀까 (이전 트리거)

미리 기준을 정해 두면 "언제 ECS로 가야 하지?"를 고민할 필요가 없다.

| 신호 | 대응 |
|---|---|
| 다운타임에 대한 사용자 불만, 배포가 잦아짐 | ECS + ALB로 이전 |
| DB 부하 증가, 백업·복구 운영 부담 | RDS로 이전 |
| 사진 조회 트래픽이 월 100GB를 넘음 | CloudFront를 붙이거나 R2로 이전 |
| 메모리 부족 | 인스턴스 타입을 한 단계 올림 (t4g.medium) |

---

## 마치며

"늘 쓰던 정석 구성"과 "가장 싼 구성" 사이에서 **지금 단계에 필요한 만큼만** 고른 결과가 EC2 한 대였다. 익숙한 도구로 빨리 출시하고, 비용은 정석 구성의 1/3 수준으로 줄였다. 나중에 확장해야 할 때 갈아탈 길도 열어 두었다.

인프라 선택에 정답은 없다. 다만 **제약 조건을 먼저 적고, 각 선택이 되돌릴 수 있는지 따져 보면** 결정이 훨씬 쉬워진다.
